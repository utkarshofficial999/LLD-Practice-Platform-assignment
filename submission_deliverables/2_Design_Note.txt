# Design Note: Architecture, Domain Model & Trade-offs

Author: Candidate Submission
Topic: LLD Practice Platform — System Architecture & Design Choices
Format: Engineering Design Document

--------------------------------------------------------------------------------
1. System Overview & Product MVP
--------------------------------------------------------------------------------
The LLD Practice Platform is a lightweight, domain-driven application built to
provide an intuitive, feedback-rich practice experience for object-oriented design.

The core MVP consists of four main pillars:
1. Problem Catalog: Real-world engineering scenarios (Parking Lot, Elevator
   Dispatcher) with explicit domain entity requirements, starter templates, and
   scoring rubrics.
2. Three-Panel Studio:
   - Left Panel: Problem specification, requirements checklist, and live entity badges.
   - Center Panel: Multi-tab workspace with TypeScript code skeleton editor, live
     visual Mermaid UML diagram, and architectural rationale notes.
   - Right Panel: AI Architect scorecard with rubric evaluations, anti-pattern
     diagnostics, and version diff reports.
3. Hybrid Evaluation: A deterministic structural linter combined with an AI
   architectural rubric that cites specific lines of evidence.
4. Version Comparison Engine: Automated tracking across versions (v1 -> v2) with
   an interactive modal highlighting resolved concerns and score improvements.


--------------------------------------------------------------------------------
2. The User Journey
--------------------------------------------------------------------------------
A typical learner session follows this flow:

1. Select Problem:
   The candidate chooses a problem from the dropdown. The system loads the
   problem description, domain entity checklist, and starter code template.

2. Model & Refine:
   The candidate edits class and interface declarations in the Code tab. In the
   Rationale tab, they document assumptions, concurrency considerations, and
   chosen design patterns. The UML tab renders their classes visually in real-time.

3. Submit for Evaluation:
   The candidate clicks "Run Evaluation". The platform transitions the submission
   through an explicit lifecycle: SUBMITTED -> EVALUATING -> COMPLETED.

4. Review Actionable Feedback:
   The candidate reviews:
   - Entity Coverage: Which required concepts were modeled vs. missed.
   - Anti-Pattern Warnings: Flags such as God Classes (>= 6 methods) or concrete
     coupling without interface abstractions.
   - Rubric Scorecard: Ratings (1–5) across 5 criteria, each paired with direct
     code evidence and concrete suggestions for improvement.

5. Refactor & Compare:
   The candidate refactors their code to address the feedback and submits again.
   The system increments the version (v2). When at least two versions exist, the
   "Compare (v1 vs v2)" button enables a side-by-side progression report.


--------------------------------------------------------------------------------
3. Domain Architecture (Clean Architecture)
--------------------------------------------------------------------------------
The core domain (`src/core/domain/`) has zero external framework dependencies:

• Problem:
  Represents an LLD problem. Contains description, difficulty, required entity
  names, expectations, rubric criteria, and starter templates. Provides
  `checkEntityCoverage()` to compare candidate class names with expected entities.

• Attempt (Aggregate Root):
  Manages a candidate's practice session for a specific problem. Tracks an
  immutable history of submissions (`Submission[]`) and maps them to versioned
  evaluations (`EvaluationResult[]`). Guarantees that history cannot be mutated.

• Submission (Entity):
  Captures a candidate's design at a specific point in time. Manages an explicit
  state machine: SUBMITTED -> EVALUATING -> COMPLETED or FAILED. Includes an
  idempotency key to safely handle duplicate submissions.

• ISubmissionContent (Strategy Pattern):
  An interface that encapsulates the content of a submission:
  - `getClassSkeleton(): string`
  - `getRationale(): string`
  - `getDiagramMermaid(): string`
  - `extractStructuralModel(): StructuralModel`
  This abstraction ensures the core domain never cares how the design was entered
  (whether typed code, JSON canvas, or an uploaded diagram).

• IEvaluationStrategy:
  A pluggable evaluation interface with a single contract:
  `evaluate(submission, problem): Promise<StageEvaluationResult>`

• CompositeEvaluator:
  Composes multiple evaluators (deterministic rules engine + LLM rubric evaluator)
  into a unified execution pipeline. Allows adding new review stages seamlessly.

• PracticeService:
  Application service orchestrating the full loop: `listProblems()`, `getProblem()`,
  `startAttempt()`, `submitAttempt()`, `retryEvaluation()`, `compareAttemptVersions()`.


--------------------------------------------------------------------------------
4. Passing the Candidate Guide's Two Change Tests
--------------------------------------------------------------------------------
The Candidate Helping Guide emphasizes architectural resilience against future
requirements. Our system passes both change tests cleanly:

• Change Test A: New Submission Formats (e.g. JSON canvas, interactive diagram)
  - Question: If the platform supports diagram-first submissions tomorrow, how
    much of the domain model needs to change?
  - Answer: ZERO domain changes.
  - Reason: `Submission` delegates to `ISubmissionContent`. We only need to write
    a new class (e.g. `CanvasSubmissionContent`) implementing `ISubmissionContent`.
    `Problem`, `Attempt`, and all `Evaluators` remain completely untouched.
  - Verified: Unit-tested in `tests/change_tests.test.ts`.

• Change Test B: New Evaluation Strategies (e.g. Human reviewers or rule linters)
  - Question: If we add human mentors or an automated AST linter, do we have to
    rewrite the practice flow?
  - Answer: ZERO changes to `PracticeService` or `Attempt`.
  - Reason: `CompositeEvaluator` implements the Open-Closed Principle. New evaluators
    simply implement `IEvaluationStrategy` and plug into the composite via
    `composite.addStrategy(new HumanReviewEvaluator())`.
  - Verified: Unit-tested in `tests/change_tests.test.ts`.


--------------------------------------------------------------------------------
5. Hybrid Evaluation: Best of Both Worlds
--------------------------------------------------------------------------------
Evaluation is split into two complementary layers:

1. Deterministic Static Linter (Fast & Objective):
   - Extracts all class and interface names using regex/AST tokens.
   - Calculates domain entity coverage against the problem's required concepts.
   - Flags concrete design smells:
     * God Class: Any class with 6 or more methods.
     * Lack of Abstraction: Designs that define classes without any interfaces.
     * Missing Concepts: Flags specific entities that were omitted.

2. AI Architectural Rubric (Nuanced & Contextual):
   - Evaluates 5 balanced criteria:
     1. Requirement Coverage (25% weight)
     2. Single Responsibility & Cohesion (20% weight)
     3. Coupling & Abstraction Depth (25% weight)
     4. Extensibility & Patterns (15% weight)
     5. Trade-off Reasoning & Assumptions (15% weight)
   - Every rating requires:
     * A score from 1 to 5
     * Exact quote/evidence citation from the submission
     * Specific concern identified
     * Concrete, actionable recommendation
   - Runs live via the Groq LLM API with an automatic fallback to local heuristic
     evaluations if the network or API key is unavailable.


--------------------------------------------------------------------------------
6. Key Engineering Trade-offs & Decisions
--------------------------------------------------------------------------------
• Trade-off 1: Structured Skeletons vs. Full Runnable Code
  Requiring runnable code forces learners to spend 80% of their time fixing syntax
  errors, imports, and mock data. In real-world LLD interviews, interviewers look
  for clean class boundaries, interfaces, and trade-off justification. Skeletons
  provide maximum signal with minimal friction.

• Trade-off 2: Hybrid vs. Pure AI Evaluation
  Pure LLM prompts frequently hallucinate scores or give generic advice. By pairing
  hard deterministic rules (entity coverage matrix, method counts) with structured
  LLM rubrics that require evidence citations, our feedback is consistent,
  reproducible, and trustworthy.

• Trade-off 3: Modular Monolith vs. Microservices
  Rather than introducing Kubernetes, message queues, and multiple services, we
  built a clean TypeScript modular monolith. It boots instantly, runs all 9 tests
  in under a second, deploys seamlessly to Vercel Serverless, and features an
  in-browser client service fallback for 100% availability.
