# Research Note: Low-Level Design (LLD) Practice & Evaluation

Author: Candidate Submission
Topic: LLD Practice Platform — Problem Space, Market Research & Product Direction
Format: Engineering Research Note

--------------------------------------------------------------------------------

1. The Problem: Why Learning LLD is So Frustrating
--------------------------------------------------------------------------------
Low-Level Design (LLD) is one of the most critical hurdles for software engineers
transitioning from junior coding to senior system design. In Data Structures and
Algorithms (DSA), learning is straightforward: you write code, run it against test
cases, and get an immediate pass or fail.

LLD is completely different. Design is fundamentally about managing trade-offs,
drawing clean boundaries, and anticipating future changes. When learners try to
practice LLD on their own today, they quickly hit four frustrating roadblocks:

1. No Automated Feedback Loop:
   A learner can spend 2-3 hours modeling an Elevator Dispatcher or Parking Lot
   system, write ten classes, and still have no idea if their design is clean,
   over-engineered, or violating fundamental principles like Single Responsibility
   or Dependency Inversion. There is nobody to tell them where the design smells are.

2. The "Multiple Valid Designs" Trap:
   In DSA, there is usually one optimal time/space complexity. In LLD, two wildly
   different architectures can both be valid depending on assumptions. For
   example, an Elevator can use a simple central LOOK/SCAN loop or a distributed
   event-driven car delegate. Static blog posts only present one "golden" solution,
   leading learners to falsely believe their different approach was wrong.

3. The Submission Friction (Boilerplate vs. Design):
   Existing platforms force candidates to choose between two bad extremes:
   - Full runnable code: The candidate wastes 80% of their time writing getters,
     setters, serialization logic, and syntax details instead of thinking about
     domain responsibilities and design patterns.
   - Pure plain text: Candidates write vague, hand-wavy descriptions without
     committing to concrete class boundaries or interfaces.

4. No Way to Measure Iterative Growth:
   Good design is naturally iterative: you create a first draft, spot coupling,
   and refactor. Today's learning materials are strictly passive (reading a blog
   or watching a YouTube video). They never show a learner: "Here is your Version 1,
   here are the tight couplings you introduced, and here is how your Version 2
   successfully resolved them."


--------------------------------------------------------------------------------
2. Research on Existing Tools & Alternatives
--------------------------------------------------------------------------------
To understand why learners struggle, we reviewed the main tools and methods
engineers rely on today:

• Educative / "Grokking the Low Level Design Interview":
  - What it offers: Curated text tutorials, static UML diagrams, and sample Java code.
  - The Gap: It is purely passive reading. Learners cannot test their own original
    ideas or get their design critiqued.

• GitHub Repositories (e.g., awesome-low-level-design):
  - What it offers: Community implementations of classic interview problems.
  - The Gap: Quality varies drastically. There is no explanation of trade-offs, and
    learners have no way to evaluate whether the code adheres to clean principles.

• LeetCode / HackerRank OOP Questions (e.g., "Design Underground System"):
  - What it offers: Interactive code editor with automated unit tests.
  - The Gap: It tests runtime output, NOT design quality. A 1,000-line God Object
    with public static variables will pass all tests as long as the methods return
    the right values.

• Paid 1-on-1 Mock Interviews (Pramp, Interviewing.io):
  - What it offers: Great human feedback from senior engineers on trade-offs.
  - The Gap: Prohibitively expensive ($150–$300 per session), unscalable, and
    dependent on the individual interviewer's personal preferences.

• Generic AI Chatbots (ChatGPT, Claude):
  - What it offers: Fast conversational feedback when pasting design code.
  - The Gap: Highly unanchored. Feedback is either generic flattery ("Great job!")
    or arbitrary suggestions ("Consider using Factory Pattern") without citing
    specific evidence in the code or maintaining a structured rubric over time.


--------------------------------------------------------------------------------
3. Key Insights & Opportunities
--------------------------------------------------------------------------------
From this research, three clear opportunities emerged:

1. Bridge Code Structure and Design Intent:
   A useful practice platform should capture both structural declarations
   (classes, interfaces, method signatures) and architectural reasoning
   (assumptions, concurrency considerations, design patterns chosen).

2. Ground Feedback in Specific Evidence:
   Instead of arbitrary 0–100 scores, feedback must be anchored to explicit
   rubrics with citations directly from the learner's submission.

3. Support Multi-Attempt Progression:
   Treat practice as an evolving conversation. Version 2 should explicitly diff
   against Version 1 to highlight what improved and what still needs attention.


--------------------------------------------------------------------------------
4. Product Direction & MVP Vision
--------------------------------------------------------------------------------
Our platform is designed around a fast, distraction-free practice loop:

   Select Problem -> Model Classes & Rationale -> Live UML Preview
   -> Submit -> Evidence-Based Feedback -> Refactor -> Compare Versions

Key Product Principles for the MVP:

1. The "Structured Design Model":
   Learners submit:
   - TypeScript class/interface skeletons (shows boundaries, access levels, methods).
   - Architectural rationale (explains trade-offs and concurrency assumptions).
   - Live UML visualizer (instantly renders Mermaid diagrams to verify relations).

2. Hybrid Evaluation Engine:
   - Deterministic Analyzer: Fast, transparent checks for mandatory domain concepts,
     God Classes (classes with >= 6 methods), and missing interface abstractions.
   - AI Rubric Evaluator: Evaluates qualitative criteria (Single Responsibility,
     Coupling, Extensibility, Trade-offs) using a strict 1–5 scale with direct
     evidence quotes from the student's submission.

3. Attempt Progression Diffing:
   When learners submit a revision, the platform compares Attempt 1 vs. Attempt 2,
   showing resolved concerns, score changes, and remaining suggestions.

This creates a high-leverage practice environment: low boilerplate, fast iteration,
and objective, actionable guidance.
