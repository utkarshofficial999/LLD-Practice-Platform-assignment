2. What We Test: Core Behavior & Invariants
--------------------------------------------------------------------------------

Group 1: Domain Invariants (`tests/domain.test.ts`)
• Entity Coverage Check:
  Verifies that `Problem.checkEntityCoverage()` correctly maps extracted class
  names against mandatory domain entities, distinguishing between present and
  missing concepts.
• Attempt Immutability & Version Progression:
  Ensures the `Attempt` aggregate root increments versions correctly (v1 -> v2),
  keeps historical submissions immutable, and pairs each evaluation with its
  corresponding version.
• Structural Token Parsing:
  Verifies that `StructuredSubmissionContent` extracts classes, interfaces, and
  method signatures reliably without requiring a full compiler pipeline.

Group 2: Evaluator Rules & Anti-Pattern Detection (`tests/evaluation.test.ts`)
• God Class Detection (Single Responsibility Principle):
  Tests that when a class defines 6 or more methods, the deterministic analyzer
  flags a "God Class Tendency" warning, citing the offending class name.
• Missing Interface Abstractions (Dependency Inversion Principle):
  Tests that if a submission defines concrete classes with zero interfaces,
  the system flags a critical "Lack of Interface Abstraction" finding.
• Composite Pipeline Orchestration:
  Verifies that `CompositeEvaluator` executes multiple evaluation strategies
  seamlessly and aggregates deterministic findings with rubric assessments.

Group 3: Candidate Guide Change Tests (`tests/change_tests.test.ts`)
• Change Test A (New Submission Formats):
  Simulates adding a new diagram-based or JSON canvas submission format.
  A new `CustomVisualSubmissionContent` class implementing `ISubmissionContent`
  is passed to the domain with ZERO modifications to `Problem`, `Attempt`, or
  the evaluators.
• Change Test B (New Evaluator Strategies):
  Simulates adding a human reviewer or rule-based AST linter. A custom
  `CustomMockHumanReviewEvaluator` implementing `IEvaluationStrategy` is plugged
  into `CompositeEvaluator` with ZERO modifications to `PracticeService` or `Attempt`.

Group 4: End-to-End Practice Loop (`tests/practice_service.test.ts`)
• Complete Multi-Attempt Flow:
  Orchestrates the full lifecycle:
  1. `listProblems()` -> returns problem catalog.
  2. `startAttempt()` -> initializes learner attempt session.
  3. `submitAttempt()` (Attempt 1) -> evaluates initial draft.
  4. `submitAttempt()` (Attempt 2) -> evaluates refactored draft.
  5. `compareAttemptVersions()` -> generates progression diff report showing
     score improvements and resolved concerns.

3. Edge Cases & Failure Modes Handled
--------------------------------------------------------------------------------
• Duplicate / Rapid-Fire Submissions (Idempotency):
  If a user double-clicks the "Run Evaluation" button, the system computes a
  content hash across the submission. If identical to the latest completed
  version, it returns the cached evaluation without creating duplicate records
  or burning redundant LLM tokens.

• Invalid or Non-Existent IDs:
  Requesting an unknown problem ID or attempt ID safely returns a clear error
  rather than throwing unhandled exceptions or crashing the server.

• Incomplete Submissions:
  Submissions missing mandatory components (e.g. empty class skeleton or empty
  rationale) are rejected early with friendly, descriptive validation messages.

• API Outages & LLM Failures:
  If the remote LLM API fails (network timeout, rate limit, or missing API key),
  the system automatically falls back to its local heuristic evaluation engine.
  The learner never receives an unhandled error or blank screen.

• Cross-Environment Portability:
  Hashing and domain logic use universal JavaScript algorithms (DJB2 + SDBM)
  rather than Node-specific globals (`Buffer`), allowing identical evaluation
  logic to execute both in Node.js and directly inside the user's browser.
