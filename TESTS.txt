3. FAILURE MODES & EDGE CASES TESTED
--------------------------------------------------------------------------------
1. Idempotent Duplicate Submissions:
   - Behavior: If the learner accidentally clicks submit twice with identical
     content, the service detects matching idempotency keys and returns the
     cached evaluation without duplicate submission records or wasted LLM calls.

2. Missing or Non-Existent Problem ID:
   - Behavior: Requesting a problem with an invalid ID throws a clean 404 error
     ("Problem with ID 'invalid' not found") rather than crashing.

3. Missing Mandatory Submission Fields:
   - Behavior: Submissions missing both class skeleton and rationale are rejected
     with 400 Bad Request ("Both classSkeleton and designRationale are required").

4. Evaluation Fallback Under API Failure:
   - Behavior: If Groq LLM API is unavailable, times out, or has an invalid key,
     the system automatically falls back to local heuristic evaluation, ensuring
     the learner always receives structured feedback.

5. Browser Universal Compatibility:
   - Behavior: Idempotency hashing uses pure JS (DJB2 + SDBM) without relying on
     Node's `Buffer`, preventing runtime reference crashes in web browsers.
